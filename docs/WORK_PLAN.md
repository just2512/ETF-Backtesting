# 实施顺序与并行开发方案

## 1. 总原则

`main` 是设计基线和集成分支。先建立统一数据契约、架构约束和验收门禁，再拆分短期任务分支。并行开发不能改变模块边界，也不能各自复制实现成交和账本。

## 2. 阶段与依赖

### Phase 0：基线与数据源核验

- 固化本文档及配置模板。
- 审计 `just2512/free-stockdb` 用户 fork，而不是只依赖上游README。
- 确认本地实际数据目录、覆盖范围、字段语义和数据授权。

### Phase 1：数据接入（可并行）

- Adapter：free-stockdb读取、字段映射、版本与来源记录。
- Data Audit：覆盖、缺失、重复、OHLC、复权、分红检查。
- Test Fixtures：构造小型、明确标注的测试数据与契约测试。

三个任务可以并行，但Adapter的输出必须遵守 `DATA_CONTRACT.md`；正式审计报告依赖真实数据。

### Phase 2：指数重叠（部分并行）

- 先开发历史成分数据模型和重叠计算算法，可使用合成fixture。
- 并行整理历史指数成分/权重来源。
- 真实历史结论必须等历史数据审计通过后生成。

### Phase 3：回测基础设施（可并行开发、统一接口）

- Indicators：布林指标纯函数。
- Execution：下一交易日成交模拟。
- Accounting：现金、份额、费用、分红账本。
- Portfolio：公共资金池与仓位约束。

其中Execution与Accounting接口需先冻结；策略模块不能自行实现替代账本。

### Phase 4：策略实现（可并行）

- A：固定定投。
- B：布林下轨买入、不主动卖出。
- C：布林买入与上轨分批卖出。
- D：多ETF公共资金池动态分配。

四组策略只产生目标动作/订单意图，统一交给Portfolio、Execution和Accounting处理。

### Phase 5：稳健性与报告

统一运行滚动区间、参数敏感性、市场阶段和成本压力测试，生成可复现报告。

## 3. 四条工作线与目录所有权\n\n具体目录所有权、冻结接口和各线验收见 [BRANCH_OWNERSHIP.md](BRANCH_OWNERSHIP.md)。首轮只创建四条工作线：\n\n- `work/data-adapter`\n- `work/data-audit`\n- `work/index-overlap`\n- `work/backtest-engine`\n\n策略A/B/C/D暂时作为 `work/backtest-engine` 内的独立模块并行实现，不再额外拆分分支。\n\n## 3. 建议分支策略

采用短期功能分支，不长期维护多条主线：

- `work/data-adapter`
- `work/data-audit`
- `work/index-overlap`
- `work/backtest-engine`

A/B/C/D策略作为 `work/backtest-engine` 内的独立模块，不再额外创建策略分支。

这些是建议命名，不要求一次全部创建。先从互不冲突的模块启动；如果只有单人/单个执行代理，多个分支并不等于真实并行算力，应按独立文件边界分派任务，避免同文件并发修改。

## 4. 合并门禁

每个分支提交前必须：

1. 说明修改范围和不修改范围；
2. 通过对应单元测试、类型/静态检查；
3. 增加契约测试或边界测试；
4. 更新必要文档；
5. 检查是否改变公共接口；
6. rebase/同步最新main后再合并；
7. 合并后运行集成测试。

以下文件/契约应由集成负责人统一控制：数据契约、配置Schema、公共账本接口、订单/成交事件模型。并行任务不得各自修改这些接口后再尝试拼接。

## 5. 更高效的推进方式

- **先冻结契约，再并行实现**：先确定DataFrame/实体字段、时间语义、缺失值语义和错误类型。
- **按文件所有权拆任务**：每个分支拥有独立目录；共享接口通过小型契约变更单独合并。
- **先跑小样本端到端**：用合成fixture贯通 Adapter→Audit→Signal→Execution→Ledger→Report，再扩大真实数据范围。
- **测试分层**：单元测试并行；契约测试在模块边界；集成测试在合并后；真实数据验收单独执行。
- **CI按路径分组**：文档检查、数据模块测试、策略/引擎测试可分组运行；最终main仍需完整测试。
- **数据与代码分离**：本地行情、缓存、报告大文件不进Git；仅提交schema、样例和生成器。
- **减少无效分支**：短任务可直接在main完成；预计会并行开发、改动范围清晰的任务才开分支。

## 6. 首轮建议执行顺序

1. 核验free-stockdb fork及本地数据可访问性。
2. 定义并实现标准数据契约与Adapter骨架。
3. 并行实现数据审计规则和合成fixture。
4. 取得真实审计结果后决定指数重叠数据补齐路径。
5. 再进入统一账本和回测引擎开发。

## 7. 停止条件

发现架构冲突、数据语义不明、账本不守恒、未来函数、数据授权问题或不可逆数据操作时停止相关任务并报告。普通格式、lint或非关键测试失败应继续修复，不应以此终止整个工作流。
